# Service Zone Optimization — разбор решения

Команда «Шмяндекс», TechArena 2026, трек Service Zone Optimization (тестирующая система NSUts).

## 1. Задача

Есть объекты инфраструктуры и потенциальные сервисные офисы. Нужно решить:
- какие офисы открыть;
- какие объекты закрепить за каждым офисом, то есть нарезать зоны обслуживания;
- каких специалистов посадить в каждый офис.

Максимизируется

```
Σ reward(s) − Σ distance(o, s) − Σ cost(o) − α · (max tasks(o) − min tasks(o))
```

при строгих ограничениях:

- **закрепление:** объект закреплён не более чем за одним офисом;
- **вместимость:** у офиса не больше `maxSize(o)` объектов;
- **баланс:** число объектов любых двух открытых офисов отличается не больше чем на `A`;
- **навыки:** каждая задача объекта покрыта навыком одного из работников его офиса, а работник состоит не более чем в одном офисе;
- **геометрия:** зона (её объекты плюс сам офис) выпуклая, и в пересечении двух зон нет ни одного объекта.

Расстояния — дорожные, их задаёт матрица «офис × объект», а не евклидова метрика.

Оценка: 11 скрытых тестов, каждый запускается 3 раза, результаты усредняются. На тесте балл равен нашему значению, делённому на лучшее значение среди всех команд, так что максимум суммы — 11. Решение собирается и запускается в Docker (`make build`, `make --silent run`) с лимитом 300 с и 8 ГБ памяти.

## 2. Почему это трудно

- **Ограничения сцеплены.** Выпуклость и непересечение зон, окно по числу объектов `A`, покрытие навыков и штраф `α` за разницу нагрузок влияют друг на друга. Обычная кластеризация (k-means, Вороной) почти никогда не даёт допустимого ответа.
- **Ловушки «всё или ничего».** При `A = 0` и большом `α` все открытые зоны должны иметь одинаковое число объектов и одинаковую нагрузку. Локальный поиск не может открыть ещё один офис: для этого нужно сразу перестроить все зоны. Поэтому он застревает на одном-двух офисах, хотя оптимум — три-четыре зоны.
- **Разброс размеров огромный:** от десятков до миллиона с лишним объектов, от 2 до тысяч офисов, до сотен навыков. Любой квадратичный шаг без контроля времени на большом входе превращается в таймаут, то есть в 0 за тест.

## 3. Устройство решателя

Один файл на C++17 (`solution/main.cpp`), около 14 тысяч строк. Решатель работает «по всему времени»: заканчивает к ~250 с при лимите 300 с.

### 3.1. Подготовка
- Пространственная сетка (CSR) для быстрых запросов «какие точки внутри оболочки».
- Выгоды `reward − distance` для каждой пары «офис — объект».
- Маски навыков и типы работников. Если навыков больше 256, частым даются свои идентификаторы, а редкие идут в общий резервный.

### 3.2. Портфель стартовых конструкций
- **Веера и полосы.** Разбиение плоскости лучами или полосами вокруг центра; DP по угловому порядку подбирает границы зон.
- **Триангуляция и хорды.** Для офисов, стоящих на «кольце» вокруг облака точек: DP по осям и уровням нагрузки, затем отжиг по хордам.
- **Power-диаграммы** (взвешенный Вороной). Веса подбираются так, чтобы каждый офис строго лежал в своей ячейке и зоны выходили выпуклыми по построению.
- **Простой строитель.** Вороной, жадное распределение команд и подбор общего уровня нагрузки `(c, x)` для штрафа `α`.
- **Лучший одиночный офис** — считается точно.

### 3.3. Поиск структуры при малом числе открытых офисов
- Перебираются наборы из 2–6 офисов из пула лучших по одиночной ценности. Для каждого набора подбираются веса power-диаграммы и распределение команд работников.
- Навыки с одинаковым набором носителей сливаются в классы. Это точное преобразование, оно уменьшает перебор.
- Пул формируется по различным местам: офисы, стоящие в одной точке, не вытесняют остальные.
- Для офисов вне облака точек есть дополнительные старты: генераторы смещаются к центру лучших объектов своего офиса, и строятся Y-разбиения на три зоны.
- **Для большого числа офисов** — отдельный поиск структуры: точное DP «выгода зоны при нагрузке ровно T» и свёртка по общему уровню.

### 3.4. Отжиг
- Несколько процессов через `fork`, у каждого свой старт и сид.
- Ходы:
  - перенос объекта;
  - перенос зоны целиком;
  - открытие и закрытие офиса;
  - вставка и выталкивание объектов;
  - смена навыков и команд;
  - «лестница» общих уровней нагрузки.
- Выпуклые оболочки поддерживаются инкрементально. Для каждой зоны хранится отсортированный список ключей точек. Конфликт с чужими точками проверяется по сетке.

### 3.5. MIP-доводка
- Из найденных решений собирается пул кандидатных зон, и задача выбора зон решается в HiGHS.
- **Маршрут A:** HiGHS статически вшит в `solve_mip`.
- **Маршрут B:** `mip_driver.py` с `highspy` общается с решателем через каналы.
- Если ничего из этого не собралось, работает чистый решатель.

### 3.6. Надёжность вывода
- Каждый промежуточный ответ записывается только после независимой проверки: оболочки пересчитываются с нуля по назначению.
- Если финальный кандидат вдруг не прошёл проверку, пишется последний проверенный ответ, а не пустой.
- В stdout ничего не печатается.

## 4. Как проверялась каждая версия

1. **Стенд семейств.** Генераторы экземпляров подбирались по публичному рейтингу. Например, по «ценности лучшего одиночного офиса», которая совпадает у команд, выдающих один офис, и по характерным уровням значений на тестах. На стенде гонялись A/B-сравнения версий: по 2–3 сида, 250 с и укороченное время 100–110 с как имитация медленного судьи.
2. **Регрессионный набор** из 31 случая с официальным валидатором: открытые примеры, вырожденные входы, более 256 навыков, совпадающие точки и т. п.
3. **Имитация судьи в Docker** с тем же образом и лимитом 8 ГБ, на 1, 2 и 4 ядрах, под нагрузкой.
4. **Стресс-тесты и фаззинг.** 171 случайный вход до 1.3 млн объектов и 2000 офисов. Фаззинг нашёл три скрытых худших случая, которых не было видно на 11 тестах:
   - квадратичное удаление из отсортированного списка при закрытии огромной зоны;
   - фаза точного выравнивания нагрузок без контроля времени;
   - простой строитель, зависавший на десятки минут на кольце из 10⁶ объектов.

   Все три исправлены: проверки часов внутри циклов и пакетное обновление.
5. **Код-ревью и санитайзеры** (ASan/UBSan) перед каждой отправкой.

## 5. Результаты

- **Лучшие замеры судьи** — до **10.48 из 11** (по лучшим результатам команд на момент подсчёта). Большинство тестов на уровне 0.99–1.00.
- **Самый трудный тест** — около 0.76 от лучшего. Это тест с ловушкой «всё или ничего» из раздела 2. Мы проверили шесть гипотез о его устройстве; на каждой реконструкции решатель выходит на уровень лидеров, но на настоящем тесте прорыва не случилось.
- **Финальная версия**, она лежит в `solution/`:
  - +5.0 % к предыдущей сборке на стенде при 250 с;
  - +8.8 % к ранней опорной версии при 110 с.
- **Призовые места** (1–3) команда не заняла.

## 6. Что вынесли

- Запас по времени и проверки часов во **всех** циклах важнее последних процентов качества: один таймаут стоит целого теста.
- Шум судьи (±0.15 по сумме) сравним с разницей между версиями. Выбирать нужно по широкому стенду и нескольким замерам, а не по одному числу.
- Фаззинг и стресс-тесты стоило завести с первого дня: самые опасные ошибки нашлись именно там.
- Подгонка под угаданные семейства скрытых тестов даёт мало, если гипотеза о тесте неверна. Общие улучшения окупаются надёжнее.
